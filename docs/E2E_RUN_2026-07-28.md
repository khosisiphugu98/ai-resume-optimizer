## 4. Tailoring

24 jobs attempted in the clean pass: **19 tailored, 5 failed**.

The 5 failures break down as **4 untailored-CV guard + 1 optimiser timeout** —
and the guard firing is correct behaviour, not a fault:

```
job1601  Data Quality Analyst (English)        — export would be the untailored base CV
job1678  Marketing Specialist – Talent Acq.    — export would be the untailored base CV
job1950  Digital Marketing Manager             — export would be the untailored base CV
job2629  Marketing Strategy Manager (Remote)   — export would be the untailored base CV

```

PR-0a is doing exactly what it was written to do: it refuses to mark a job
`tailored` when the optimiser changed nothing. Roughly **1 in 6 jobs (17%)**
produces no meaningful tailoring, which is a conversion leak worth understanding
even though the guard makes it safe.

### But the guard cannot see cross-job duplicates — and they are still happening

28 CVs were produced this run. Hashing the extracted text layer:

```
28 PDFs  ->  25 distinct documents
1 duplicate group of 4  =  14% of output is text-identical to another job's CV
```

The group:

```
Khosi_Siphugu_CV_Canonical_Marketing_Associate_921.pdf             (7733 chars)
Khosi_Siphugu_CV_HYRAX_PPC_Manager_2638.pdf                        (7733 chars)
Khosi_Siphugu_CV_Jellyfish_Programmatic_Advertising_Specialist_1027.pdf
Khosi_Siphugu_CV_Meridial_..._Business_and_Management_Specialist_1833.pdf
```

These are four different jobs, with four different JDs (5686 / 2576 / 3498 / 2704
chars) and **four different computed match scores (38, 53, 67, 38)** — yet
byte-identical output text. The optimiser measured different relevance and wrote
the same document.

This is a real gap in the guard's design, not a regression. PR-0a compares a
document **against itself** before and after optimisation, so it catches
"optimisation changed nothing". It cannot catch "optimisation changed the same
things for unrelated jobs". The duplicate rate is essentially unchanged from the
11.6% measured on 27 July.

**Fix:** hash the exported text and compare against the other CVs already on
disk, not only against the pre-optimisation document.

  to 159-paths collision from the audit is gone.
- Text length is healthy: 7733 / 8282 / 8678 chars (min / median / max) against a

- The skill-suggestion gate holds. Unevidenced skills seen this run

## 7. Reading the job description — the gap the operator identified

The operator's instinct is correct and the data supports it. `jd_text` is passed
into the answer context (`run.js:172`) and into the email composer, so the model
can *reason* from it — but **nothing extracts explicit instructions from a JD and
acts on them**. There is no instruction-extraction step anywhere in the pipeline.

Measured across 2465 stored JDs:

| instruction pattern | JDs | share |
|---|---|---|
| portfolio / work samples requested | 331 | 13.4% |
| reference / quote code | 106 | 4.3% |
| closing date stated | 99 | 4.0% |
| **explicit "send your CV to `<address>`"** | **50** | **2.0%** |
| complete an assessment / test | 37 | 1.5% |
| cover letter required | 23 | 0.9% |
| subject-line instruction | 20 | 0.8% |

The sharpest case is routing. Of the 50 JDs that name an address to apply to, the
classifier already routes **39 correctly to `email`**. The other **11 are
misrouted**:

```
352   unknown     pearl@apmfglobal.com              Information Technology Project Coordinator
422   unknown     hr@cosmoict.co.za                 Internal Account Management Consultant
529   unknown     careers@parklands.co.za           IT Support Technician
547   unknown     legal@metricgroup.net             Maintenance Foreman

```

All 11 are currently rejected on fit, so nothing was misapplied — but the

Also worth noting: `legal@metricgroup.net` was extracted as the apply address for

### Recommendation (for the follow-up, not this run)

Add a JD instruction-extraction pass at enrich time that writes a structured
`jd_instructions` column, then have each channel consume it:

1. **Route override** — an explicit "send CV to X" outranks the scraped apply
   control. Fixes the 11 misroutes above.
2. **Reference code / subject line** — feed into `buildSubject` so the email
   carries the reference a recruiter filters on.
3. **Portfolio / assessment / cover letter required** — currently invisible.
   13.4% of postings ask for a portfolio; an application that silently omits a
   required artefact is a wasted send. These should either be satisfied from the
   profile or routed to `manual_required` with the reason stated.
4. **Closing date** — cheap prioritisation signal, currently unused.

## 8. Defects found by running the system

Ordered by value. Every one of these was found by running the pipeline, not by
reading it.

### D0 — The model's "I cannot answer this" token was typed into a form and sent ← most severe

The first application this run submitted, to **Gulf Associates**, contains:

```
[llm] Portfolio / work samples   =>  "unanswerable"
```

That string was typed into the employer's form and submitted. The whole design
of this system is *park rather than guess*; here it filled a field with its own
internal marker for "I can't answer this" and sent it under the candidate's name.

**Mechanism.** `batchMap` gives the model two channels — a `fills` array and an
`unanswerable` array (`resolver.js:325`). The model put the field in `fills`
with the *value* `"unanswerable"` instead of putting it in the `unanswerable`
array. `settleModelValue` (`resolver.js:523`) then:

- parks on `null`/`''` (`:530`) — passes, the string is non-empty;
- validates against `field.options` (`:538`) — skipped, this is free text;
- runs `guardAnswer` — which covers years, work authorisation, credentials,
  location and salary, and has no concept of a non-answer sentinel.

So it was accepted as an ordinary answer at tier `llm`, logged like any other
fill, and typed. Nothing in the pipeline distinguishes a refusal expressed as
prose from a real answer.

**Scope.** A scan of every `filled_json` ever recorded finds exactly **one**
occurrence — this one. It is rare. It is also the *only* application this run
auto-submitted, which is the whole problem: on the auto-submit path there is no
human between the sentinel and the employer.

**Fix** — one guard in `settleModelValue`, immediately after the empty check:

```js
if (/^(unanswerable|unknown|n\/?a|none|not applicable|no answer|i (don'?t|do not) know)$/i
      .test(String(value).trim()))
  return park('llm', 'model returned a non-answer sentinel as a value');
```

Worth doing today, and worth pairing with a pre-submit assertion that no value
about to be sent matches that pattern — a sentinel reaching the fill layer is a
bug wherever it came from.

### D1 — The years-of-experience matcher is punished for succeeding ← highest value

`answer/resolver.js:189-199`:

```js
const skill = extractSkill(ctx.question);
if (!skill) {
  const total = p.current?.confirmed ? p.current.totalYearsExperience : null;
  if (typeof total === 'number') return ok(String(total));   // answers "3"
}
const { value, reason } = skillYears(p, skill);
if (value == null) return park(`years of experience with "${skill}" — ${reason}`);
```

Extracting **nothing** answers the question. Extracting **something the profile
does not list verbatim** parks it, with no fallback. The matcher is penalised
for working.

This matters because LinkedIn screener questions name a **domain**, not a tool.
Live parks from this run:

| question | extracted | in profile? |
|---|---|---|
| How many years of work experience do you have in data analysis and data profiling? | `data analysis and data profiling` | no — profile has `data analysis techniques` |
| How many years of Marketing and Advertising experience do you currently have? | `Marketing and Advertising` | no |
| How many years of Online Media experience do you currently have? | `Online Media` | no |
| How many years of Marketing experience do you currently have? | `Marketing` | no — profile has `App Marketing`, `E-Mail-Marketing` |
| How many years of work experience in creating and maintaining Source to Target mappings? | (task description) | no — correctly unanswerable |

A Marketing Data Analyst with 3 confirmed years cannot answer "how many years of
Marketing experience do you have". Because a single required park abandons the
application, this one defect is the primary cause of Easy Apply non-conversion.

**Fix — extend the mechanism that already exists.** `GENERIC_EXPERIENCE_QUALIFIERS`
(`matchers.js:315`) already returns `null` for qualifiers like `relevant
full-time`, routing them to the confirmed total. That is precisely the right
shape. Widen it to cover:

- **compound phrases** — split on `and`/`&`/`/` and match any component
  (`data analysis and data profiling` → `data analysis`);
- **stem/substring matching** against profile skills (`data analysis` should
  match `data analysis techniques`);
- **domain terms covered by the candidate's own role and title** — `marketing`,
  `advertising`, `online media`, `digital`, `analytics` are the field the
  profile's `current.title` and experience sit in; these should resolve to
  `totalYearsExperience`.

Deliberately **not** a blanket fallback: `How many years of Kubernetes?` must
still park. The distinction is domain-vs-tool, and the profile has enough to
make it.

### D2 — Cross-job duplicate CVs are invisible to the untailored-CV guard

14% of this run's output (4 of 28) is text-identical to another job's CV, across
four different JDs with four different match scores. PR-0a compares a document
against **itself** before and after optimisation, so it catches "nothing
changed" but never "the same thing changed for unrelated jobs". See §4.

**Fix:** hash the exported text against the other CVs on disk, not only against
the pre-optimisation document.

### D3 — The Greenhouse adapter misses its own EU subdomain

`adapters/index.js:17` — `/(boards|job-boards)\.greenhouse\.io/` requires
`job-boards` to sit immediately before `.greenhouse.io`:

```
job-boards.greenhouse.io/agoda/...              MATCH
job-boards.eu.greenhouse.io/clearscore/...      MISS   -> falls through to generic
job-boards.eu.greenhouse.io/agency/...          MISS   -> falls through to generic
```

Lever's matcher already handles the regional variant (`jobs\.(eu\.)?lever\.co`);
Greenhouse's does not. Two jobs in this run's batch (ClearScore, Meridial) took
the generic path — losing the vetted adapter and its submit selector, and now
subject to the stricter `mayFinish` CV-upload check.

**Fix:** `/(boards|job-boards)\.(eu\.)?greenhouse\.io/`.

### D4 — The Easy Apply collector is not scoped to the modal

Job 453 got stuck at step 3 and captured this as the page's controls:

```json
[ {"role":"textbox","name":"Search"},
  {"role":"combobox","name":"Select language"},
  {"role":"combobox","name":"Search"} ]
```

Those are **LinkedIn's own navigation chrome**, not an application form. When
the Easy Apply modal is absent or has closed, the collector falls back to the
whole page. This is the same class of bug as the CareerJunction search-bar
incident — which was fixed for the *external* path (`f67cbf0`, "pick the richest
form root", plus the search-bar filter) but has no equivalent on the Easy Apply
path.

Nothing was typed into LinkedIn's search box here, because the run got stuck
before filling. The scoping gap is real regardless.

Note also the URL carried `applicantTrackingSystemName=Workable` — the posting
was a Workable job surfaced as Easy Apply, which is how the flow ended up
off-modal in the first place.

### D5 — The submissions ledger renders correction records as extra submissions

`apply/submission-log.js:83` `listSubmissions` returns every line of
`submissions.jsonl` with no collapse by `applicationId`. The ledger is
append-only, so a corrected outcome is a *new line*:

```
3  2026-07-28T07:36:41Z  app 87  job 2136  submitted  Famous Brands
4  2026-07-28T12:09:32Z  app 87  job 2136  error      Famous Brands
```

`npm run submissions` shows **5 submissions** where there are 3 real ones and
one retracted false positive, and the retraction is displayed as though it were
a second application to Famous Brands. The `[UNCONFIRMED]` flag is the only
status surfaced; a corrected-to-`error` record gets no marker at all.

**Fix:** collapse by `applicationId`, keeping the latest record, and label
non-`submitted` outcomes explicitly. (The audit script written for this run,
`scripts/e2e-audit.mjs`, does this and reports 4 distinct applications.)

### D6 — One CLI stage's exit handler kills another stage's browser

`browser.js:139` registers `closeBrowserOnExit()` at module load for **every**
CLI command, and its handler calls `reclaimProfile()`, which SIGKILLs any Chrome
process holding the profile directory — regardless of which process launched it.

Running `npm run score` while `npm run tailor` was working killed the tailoring
run's browser mid-pass. Worse, **the tailoring process did not abort**: it kept
selecting jobs and marking each one failed, burning 12 jobs in 40 seconds with
`page.goto: Target page, context or browser has been closed` before it was
stopped by hand.

This was triggered by operator error during this run (two stages run
concurrently), but the failure mode is the bug: a long-running stage has no
recovery from a lost context and no circuit breaker on repeated identical
failures.

**Fix:** two parts — (a) record the owning pid when the context is launched and
refuse to reclaim a profile owned by a live *different* process; (b) abort the
stage after N consecutive `browser has been closed` failures rather than
consuming the backlog.

### D7 — Failed applications leave no `applications` row

Job 453 failed with `form did not advance past step 3` and no row was written to
`applications`. Only the event log records it. Across this run, **14 Easy Apply
attempts produced 3 application rows**. Any conversion metric computed from
`applications` silently omits hard failures and overstates the fill rate.

### D8 — The run summary says 0 submitted when 2 applications were sent

```
Applications complete — 0 submitted, 2 queued for review, 11 parked, 2 manual, 13 failed
```

Two applications reached employers, both recorded `submitted_unconfirmed`. The
counter only increments on outcome `submitted`, so the terminal state introduced
by PR-4b — deliberately *not* a retry, deliberately a real send — is invisible
in the one line an operator reads. Count `submitted_unconfirmed` as sent, and
name it separately.

### D9 — `isDiallingCode` only recognises the parenthesised format

`answer/matchers.js:53`:

```js
const isDiallingCode = opt => /\(\+\d{1,4}\)|^\+\d{1,4}$/.test(String(opt));
```

Live option list from job 1833 (Meridial): `United States +1 | Afghanistan +93 |
Åland Islands +358 | ... | South Africa +27`. No parentheses, so:

```
"South Africa (+27)"   DETECTED
"South Africa +27"     MISSED      <- this vendor's format
"United States +1"     MISSED
```

The list is not recognised as a dialling-code control, `identity.country` is fed
as a bare `"South Africa"`, no option matches, and the application parks. This is
the same defect PR-2c fixed — fixed only for the format the audit happened to
capture.

**Fix:** `/\(?\+\d{1,4}\)?(\s|$)/` plus a prefix match so `South Africa` fits
`South Africa +27`.

### D10 — A marketing opt-in was answered because the label contained "Email"

On the Agoda submission, at tier **profile** (deterministic, no model involved):

```
Q: "Email me about other job openings within the Booking Holding's entities
    and recruitment-related newsletters"
A: "mksiphugu@gmail.com"
```

The email matcher fires on the word "Email" and does not distinguish *"what is
your email address"* from *"email me marketing"*. The candidate has been opted
into a recruitment newsletter by a keyword match.

**Fix:** the email matcher should require the label to be *asking for* an
address (`email address`, `e-mail`, `contact email`) and decline imperative
phrasings (`email me`, `send me`, `subscribe`, `newsletter`, `updates`). The
`declines a label that merely overlapped` mechanism added for city-vs-country is
exactly the right tool.

### D11 — Consent questions are answered by the model with no policy behind them

Also on the Agoda submission, all tier `llm`:

```
Do you agree to Agoda's use of personal data ... we may collaborate and
  share your data with [third parties]?            => "Yes"
Do you allow us to provide you TEXT/SMS updates?   => "Yes"
To avoid ... impairment of our parent company's
  independent auditor – Deloitte ...               => "No"
```

The first two are legally meaningful consents granted on the candidate's behalf
by a language model with nothing in the profile expressing a preference. The
defaults chosen are defensible, but they are the model's defaults, not the
candidate's.

The third is a compliance attestation. It was answered `No` here and **parked**
on job 2128 — the same question, on the same posting, handled two different ways
in one batch.

**Fix:** add a `consent` block to the profile (`dataSharing`, `marketingEmail`,
`smsUpdates`) and resolve these deterministically, defaulting to the
privacy-preserving answer where unset. Consent is not something to infer.

### D12 — The same form is filled twice

The Agoda submission recorded **31 fields for 18 unique questions** — 13 of them
filled and logged twice with identical values. The likely cause is form-root
selection picking a container that holds two copies of the control set (a
responsive/mobile duplicate, or nested forms), which the "pick the richest form
root" change (`f67cbf0`) would tend to favour.

Harmless to the employer, but it doubles the model spend per application and
makes every field-count metric wrong.

### D13 — URL dedupe misses query-string variants

`appliedUrlOwner` compares the full resolved URL. Two LinkedIn cards for the
same Agoda posting resolved to:

```
job 1490 -> job-boards.greenhouse.io/agoda/jobs/5794753?gh_src=ec760f9d1
job 2128 -> job-boards.greenhouse.io/agoda/jobs/5794753?gh_src=e13c735b1
```

Same Greenhouse job `5794753`, different tracking parameter — so the duplicate
guard did not fire. **Job 1490 was submitted, and job 2128 then filled the same
posting again**, stopped only by an unrelated park on the Deloitte question. The
dedupe added in PR-4a is real but too literal.

**Fix:** normalise before comparing — strip the query string, or at minimum the
known tracking params (`gh_src`, `utm_*`, `referralCode`, `igbTracker`).

## 9. The email application — drafted, verified, and held

One job survived to a send: **job 648, Business Intelligence Engineer @
amplify5, fit 65**, address `Mina.tyhaliti@amplify5.co.uk` extracted cleanly.
(The second, job 1835, failed tailoring — the untailored-CV guard refused it.)

The draft was composed and queued. **It has not been sent.** Reviewing the
covering letter against the profile before release found a fabricated claim:

> "My proficiency in SQL and familiarity with cloud technologies, **including
> Azure**, align well with the requirements for maintaining and optimizing SQL
> Server data warehouses and supporting the transition to Microsoft Fabric."

**Azure appears nowhere in the profile.** The profile has generic `cloud
platforms`, `cloud environments`, `cloud infrastructure` — never a named
provider. The JD asks for Azure and Microsoft Fabric, and the model closed the
gap by naming the technology the employer wanted.

Every other claim in the letter verifies:

| claim | profile |
|---|---|
| ETL processes | `ETL`, `ETL pipelines` ✅ |
| SQL, Power BI | `SQL`, `Power BI` ✅ |
| data engineering, business intelligence | both present ✅ |
| "recent studies in Marketing, Statistics and Quantitative Methods" | UCT postgraduate study, exact match ✅ |
| three years' experience | `totalYearsExperience: 3` ✅ |
| **Azure** | **absent** ❌ |

This is the gap §5b of the audit named and nothing has closed: **the CV pipeline
has a fabrication guard; the covering letter — the document a human reads first
— has none.** The prompt forbids invention; nothing checks the output. Here the
check took one grep.

**Fixed, same day.** `src/email/verify.js` now runs every letter through an
evidence gate before it can be queued: proper nouns and product names are
extracted per sentence, and each must appear in the profile or the evidence
corpus. **The job description deliberately does not vouch for anything** — the
JD is where the invented term came from.

On a miss the composer regenerates once, naming the offending terms; if the
second attempt also invents something, it falls back to the deterministic
profile-only body, which is assembled from profile fields and cannot claim
anything the candidate does not have.

Run live against this posting, the gate caught **two** fabrications in the first
draft — `Azure` **and `Power BI Premium`**, a paid tier the profile does not
have — rewrote, and passed. The letter that went to amplify5 claims only SQL,
Python, Power BI, ETL and data validation, all of which the profile and CV
support.

Checked against the one letter this system had previously sent, the gate also
independently catches the recruiter/end-client confusion recorded in §5b of the
audit: it flags `GEAR` in a letter addressed to Resource Complete.

Also still open from the audit, both visible on this draft:

- **`buildSubject` remains dead code.** The subject is
  `"Application for BI Engineer Position"` — no candidate name, no reference,
  and it abbreviates the real title ("Business Intelligence Engineer"). A
  recruiter cannot search for it.
- **`reference_number` is `null`**, though the column exists.
